# 从 PRD 提取逻辑与流程

## 先做映射，再画页面

读取输入 PRD 后，先列出三张内部映射表：

1. **流程节点 → 页面编号**：用户实际需要操作或查看的节点必须映射到 `H-01`、`D-01` 等页面；纯系统步骤保留为不跳转节点。
2. **页面 → 逻辑链**：每个页面的入口、操作、系统判断、状态变化、结果和边界。
3. **PRD 规则 → 页面表现**：每条频率、权限、状态或数据范围规则，要能定位到一个页面状态或功能概览条目。

不要根据视觉稿推测规则；PRD 未说明的交互、权限或异常标为「待 PRD 明确」。

## 业务图示映射

存在业务流程或交互时，绘制前必须读取 `diagram-rules.md`。从 PRD 文字提取逻辑，不要求 PRD 预先带图。

- 将关键规则映射到「依据章节/规则 → 图编号 → 节点、判断边或消息 → 对应页面/只读系统步骤」。复用原有内部映射表，不另造一份需求文档。
- 流程图、时序图、状态图分别表达路径、协作顺序和对象生命周期；按适用性组合，不相互替代。
- 只有 PRD 明确的先后关系才画前后箭头。配置生效、业务事件和用户进入可能是不同触发入口，不能为了横向排版强串成连续步骤。
- 分支在图内写清条件及去向；“不展示”“未受理”“处理失败”若业务含义不同，不合并成一个失败节点。
- 不限制主链节点数；复杂时按场景/阶段拆图并标明衔接，保持规则完整。图示实现、示例与验收见 `diagram-rules.md`。

## 页面逻辑卡

每个页面按需使用以下三组，信息缺失的组不凑数：

| 分组 | 必须回答的问题 |
|---|---|
| 组件与交互 | 用户能操作什么？操作后去哪里或触发什么？ |
| 逻辑说明 | 满足什么条件？系统如何判断/计算？什么数据或状态改变？ |
| 边界处理 | 何时为空、禁用、失败、无权限或不可恢复？ |

一条逻辑优先写成完整因果链，避免拆成无关系的短句。数据表字段、接口和算法实现细节不搬到原型；只保留会改变页面行为的业务规则。
